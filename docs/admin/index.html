SIMPLE, NOT SHORTCUTS

A little peace of mind.

How your release studio works—and what it deliberately doesn’t do.

01

Connect safely.

Create a fine-grained GitHub token for glitchyapi/seva-saathi-pro only. Give it Contents: read/write and Actions: read/write. Choose a short expiry.

The token stays in this tab’s memory. Refreshing or disconnecting removes it. Never reuse a broad token posted in a chat.

Create a scoped token ↗
02

Publish from your code.

Commit interface changes to web/, or Android changes to app/. This studio starts the release workflow from the latest main branch.

The workflow signs the manifest, uploads changed public files to OnlyFiles with a GitHub fallback, and updates one stable URL. Native releases also build and sign a real APK.

View release workflow ↗
03

Know the boundaries.

Background alerts use Android’s best-effort six-hour checks, not instant push. Opening the app checks again. A push provider can be added in a later native release.

Android needs user confirmation for APK installs. There is no silent installation, on-device rebuilding, or access to users’ private journals.

04

Keep your keys.

Back up your Android signing keystore and update-signing private key securely. Future updates must use these same keys.

Required repository secrets: APK_KEYSTORE_B64, APK_STORE_PASSWORD, and UPDATE_PRIVATE_KEY. Never place them in repository files or this page.

OnlyFiles is used for verified public release files, with a GitHub fallback. Its upload API returns a landing page: the Android downloader resolves a fresh binary link without executing the page, then verifies the SHA-256. Only app files are uploaded—never journals or signing keys.
